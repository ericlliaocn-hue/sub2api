# 子池隔离与 Cyber 归因 — 实施说明书

> 状态：Phase A / B / C 已实现；Phase D 信誉分已实现，同步审核超时改造待决策（见 §7 Phase D）  
> 目标：在**对外一个展示分组、一个标价倍率**的前提下，用内部子池缩小共号半径、透明同组负载、观察期日抛号、池冷却后清白 Key 自动迁移，并保证出事能归因到具体 API Key。  
> 非目标：不靠改 UA / 指纹源码规避上游限流；不把本方案做成「解 server_overloaded」的药。  
> 与现有能力关系：不同于 `COMPOSITE_GROUPS.md`（按模型路由到不同厂商）。本方案是**同一展示分组内的账号共用水域拆分**。

---

## 1. 背景与成功标准

### 1.1 要解决的问题

1. 多人共用少量上游号时，一人破限 / cyber，整池受损且难追责。  
2. 需要可展示、可计数的同组透明度，便于自查与对时间线。  
3. 新 Key 不能直接进入正号池，需先过观察期（日抛炮灰号）。

### 1.2 成功标准

- 用户购买 / 选择时仍只见一个分组（如 `Pro`）和一个标价倍率。  
- 任一请求可回答：`user_id`、`api_key_id`、`group_id`、`sub_pool_id`、`account_id`、时间、结果。  
- 某上游号进入冷却后：可列出时间窗内 Top Key；`clean` Key 自动迁走；`suspect` 留审；可对 clean 用户补偿。  
- 同子池用户可见：人数、各匿名成员的首次/最后调用、当天次数、近 7 天次数。

---

## 2. 概念模型

```text
展示分组 Group（用户可见，一个倍率）
├── 正式子池 Sub-pool × N     ← 正号；人数与同伴用量可见
└── 观察池 Probe pool         ← 日抛 / 炮灰号；新 Key 默认进入
        └── API Key 绑定（同一时刻只进一个子池）
                └── 上游 Account（通常 1 主 ± 1 备）
```

| 概念 | 对谁可见 | 职责 |
|------|----------|------|
| Group | 用户 + 管理端 | 商品、标价倍率、可选模型 |
| Sub-pool | 用户见「本组」摘要；管理端见全部 | 挂载账号、容量、健康、绑定 Key |
| Probe pool | 用户可见为观察/试用节点 | 与正式池账号物理隔离 |
| Key ↔ Sub-pool 绑定 | 用户见当前组负载；管理端可改 | 调度边界；迁移写审计 |

**标价倍率**：始终跟 Group，不按子池、不按信誉拆成多个对外倍率。  
**处罚**：Key 限速 / 封禁 / 打回观察池 / 拒绝进正池；经济惩罚若做，用独立账单项，不改 Group 倍率展示。

## 3. 用户可见信息（定稿）

同子池（含观察池）成员看板，**按 API Key 一行**，身份匿名：

| 字段 | 口径 |
|------|------|
| 成员 | 池内稳定匿名代号；当前用户行标「我」 |
| 开始调 API | **进入当前子池之后**的首次「计入」调用时间 |
| 最后调用 | 最近一次计入调用时间 |
| 当天次数 | 站点时区（默认 `Asia/Shanghai`）自然日 0:00–24:00 |
| 近 7 天次数 | **滚动 7×24 小时**（含此刻往前 168h） |
| 本组人数 | 当前绑定在本子池的 Key 数（或「占用名额」） |

### 3.1 计入规则

- 计费或上游已受理的请求计 1 次；流式整段算 1 次。  
- 纯客户端失败、未出站重试：不计。  
- 健康检查 / 内部探针：不计（若有）。  
- 迁池后：本池段统计从迁入后重计；管理端可查历史绑定段。

### 3.2 明确不展示给同组用户

他人邮箱、UID、IP、Prompt、计费金额明细、上游账号标识。

### 3.3 管理端额外可见

实名用户、Key、审核命中、子池/账号、处置按钮、迁移审计、「谁打的」时间窗报表。

## 4. 子池与账号

### 4.1 正式子池

- 每池建议 1 个主号，可选 1 个热备（仅主号不可用时上）。  
- 容量：  
  - 软上限：绑定 Key 数（可配置，如 8，非写死业务常数）  
  - 硬上限：并发、近 24h 调用量 / token（防单 Key 打爆）  
- 状态：`healthy` | `cooling` | `closed`（不接收新绑定）。

### 4.2 观察池（日抛 / 炮灰）

- 账号与正式池**禁止混挂**。  
- 用途：新用户、新 Key、观察期未满、信誉未恢复、证据不足的临时安置。  
- 号废：换日抛号，不自动把观察池流量灌进正式正号。  
- 用户文案可称「试用节点」，同样展示人数与同伴用量字段。

### 4.3 创建 Key 时分配

用户仍只选 Group（如 Pro）：

1. 默认进入观察池。  
2. **毕业条件**（实施时可配置，建议默认）：观察期 ≥ N 天 **且** 无严重审核/破限处置 **且** 用量未触发硬顶异常。  
3. 毕业后进入负载最低的 `healthy` 正式子池。  
4. 管理员可指定绑定，覆盖自动分配。

---

## 5. 池冷却与清白自动迁移

当正式子池因 overload / 降智 / 号废进入 `cooling`：

1. 停止向该池上游号调度新流量。  
2. 对池内 Key 打标（结合时间窗用量占比、审核命中、行为特征）：  
   - `suspect`：留审、限速，**不**迁入 healthy 正式池  
   - `clean`：进入自动迁徙队列  
3. `clean` Key **自动迁走**：  
   - 优先：负载最低的 `healthy` 正式子池  
   - 目标池满或全局紧张：先入观察池，再按毕业规则进入正式池  
4. 写入审计：`key_id`、从池、到池、原因、时间、操作者（`system` / admin）。  
5. 用户侧人数与看板刷新；可提示「节点已切换」。  
6. 对 `clean` 且受影响用户可按运营规则补偿（额度/天数）——补偿策略属运营配置，本说明书不绑定具体数值。  
7. `suspect` 查实后封 Key；误杀由管理员标 `clean` 后再迁。

### 5.1 防抖

- 同一 Key 自动迁移冷却：例如 24h 内最多自动迁 1 次（管理员强制迁移除外）。  
- 避免 cooling 抖动导致全站 Key 同时挤入唯一好池：迁移可排队、限速执行。

## 6. Cyber 与证据链

### 6.1 请求级必关联字段

`user_id`, `api_key_id`, `group_id`, `sub_pool_id`, `account_id`, `started_at` / `ended_at`, `outcome` / 错误类, `moderation_hit`（若有）

### 6.2 处置顺序（Key 级为主）

1. 审核命中 / 异常用量 → 记在 Key（子池汇总仅看板）。  
2. 上游号异常 → 按 `account_id` + 时间窗出 Top Key 报表。  
3. 罚肇事 Key：限速 → 打回观察池 → 封 Key →（升级）封用户。  
4. 同池他人：自动迁走 + 可选补偿；**不以同组投票作为封禁依据**。

### 6.3 第三方审核（后续阶段）

- 使用云端 Moderation API，**禁止**再以自建小模型全量同步拦主链路。  
- 高危：同步拒绝；擦边：异步计分。  
- 超时：可配置「超时放行并记未审」，避免拖垮网关。  
- 审核结果只作为 Key 信誉输入，**不修改** Group 对外倍率。

## 7. 分阶段实施

### Phase A — 对内能绑，用户见人数与同伴用量（已实现）

- 数据模型：Sub-pool、账号挂池、Key 绑定、绑定历史。  
- 调度：该 Group 下请求只使用 Key 当前子池内账号。  
- 用户：当前子池人数 + 匿名同伴表（首末时间、当天、近 7 天）。  
- 管理端：建池、挂号、绑 Key、手工迁移。

### Phase B — 观察池 + 毕业（已实现）

- 独立日抛账号池；新 Key 默认观察池。  
- 可配置毕业条件；毕业自动进正式子池。

### Phase C — 冷却与自动迁移 + 归因报表（已实现）

- 池 `cooling` 状态机；clean 自动迁；suspect 留审。  
- 管理端「谁打的」时间窗报表；Key 限速 / 封禁。  
- 迁移防抖与排队。

### Phase D — 审核计分（信誉分已实现）

- 第三方 Moderation 接入：**沿用现有链路**，未新增第三方通道。仓库里已有两套云端审核，Phase D 只消费它们的结果，不再加第三条路：
  - 内容审核 → OpenAI Moderations API，写 `content_moderation_logs`；
  - Prompt 审计 → OpenAI 兼容的 Qwen3Guard 端点，写 `prompt_audit_events`。
- Key 信誉分：`api_key_reputation` 表（迁移 236）。分数是**派生值**，由后台任务按滚动窗口从上面两张事件表重算，表本身不是事实来源；只有「已执行的处置」这一列是表里独有的状态。
  - 权重按**证据强度**给，不按内容恶劣程度：guard `critical` 25 分、`high` 12 分、`flag` 4 分；审核 `block` / `keyword_block` / `cyber_policy` 20 分，其余 flagged 命中 8 分。
  - 线性时间衰减：窗口边缘的命中几乎不扣分，Key 因此能自行恢复，不需要单独的「赦免」任务。
- 阈值驱动打回观察 / 封禁：低于「打回」阈值降级进观察池，继续下滑到「封禁」阈值才停用 Key，每轮最多升一级。已封禁的 Key 不会被重复处置。
  - 与现有的**用户级**自动封禁（审核命中满 `ban_threshold` 次禁用 `users` 行）互不覆盖：本阶段只动 Key，是 §6.2 处置阶梯里更靠前的一档。
  - 误杀可由管理员「撤销处置」。分数会随窗口自然恢复，但**处置不会自动过期**——解封是人的决定。
- 仍不拆对外 Group 倍率。✅ 信誉分只影响 Key 的去向与可用性，不参与计费。

**未做，需要决策：** §8 表里的「同步审核超时 100～150ms 放行并记未审」没有实施。现状是两条链路的失败语义相反：内容审核超时（默认 3000ms）**放行**，Prompt 审计 blocking 模式超时**返回 503 拒绝请求**。把后者从 fail-closed 改成 fail-open，等于在网关热路径上放宽安全边界，属于产品取舍而非实现细节，留给人来定。

## 9. 风险与非目标

| 风险 | 应对 |
|------|------|
| 同 Group 不同子池体验差 | 观察期、坏池快冷却、clean 快迁、补偿话术 |
| 看板导致同组甩锅 | 封禁只认证据链，不认同组指控 |
| 多开 Key 摊薄次数 | 观察期 + 按用户维度巡检 |
| 自动迁挤爆唯一好池 | 排队、目标池容量检查、满则进观察池 |
| 与 Composite Group 概念混淆 | 文档与后台文案区分「厂商路由」vs「共号子池」 |

**非目标：** 通过本方案解除上游账号已被标记的限流；修改客户端指纹以「破解风控」。

## 11. 已定产品抉择（会议结论）

1. 对外一个展示分组、一个标价倍率。  
2. 用户可见本组当前人数，以及同伴：开始调 API、最后调用、当天次数、近 7 天次数（滚动 7×24h）。  
3. 观察池单独使用日抛 / 炮灰号，与正号隔离。  
4. 池被炸后，清白 Key 自动迁走（满则先观察池）。  
5. 抓人优先于避免连坐；有证据则罚 Key，他人可补偿。  
6. 先落方案与分阶段实施；指纹相关源码暂不动。
